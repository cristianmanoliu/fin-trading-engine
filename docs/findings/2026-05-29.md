# 2026-05-29 — Layer 3 testnet reconciler self-extending IP-ban bug (found + fixed)

## TL;DR

Started from a user question ("should we rent VMs + deploy all symbols to test live/shadows harder?"). Answer was no (locked reshuffle discipline + per-key rate-limit pool, not per-machine). Investigating the rate-limit headroom surfaced a **live bug**: the Layer 3 testnet `PositionReconciler` had been **self-extending a Binance testnet IP ban for 10 days**, capturing **zero** Layer 3 parity data. Root-caused, fixed with TDD, deployed to ENS+KAVA, verified in production.

## Root cause (confirmed)

The reconciler polls testnet `/fapi/v2/positionRisk` every 60s with **no 418/429 handling**:

- The testnet IP (`15.158.242.73`, NAT-shared — 3 rotating egress IPs observed) occasionally exceeds 6000/min **collectively with other tenants** → brief 429 (only **15** ever).
- Each 429 → Binance issues a **418 IP ban** (`banned until T`).
- Binance **extends** `banned until` on **every request received while banned**.
- The reconciler's ban-blind 60s polling kept hitting the banned endpoint → **ban never cleared → 941 bans over 10 days**.
- Net effect: reconcile **never once succeeded** → `journal/layer3/` **empty** → zero parity data on the formally-required STAGE_1 gate.

**Decisive evidence:** 418:429 ratio = **941:15 (60:1)** — bans are self-inflicted by polling-while-banned, not by our call volume. Exact-60s WARN spacing confirms naive ticker, no backoff.

The sibling aggTrade poller (`pkg/marketdata/binance.go:442-452`) already handles this correctly — 60s backoff on 418/429, never exits the loop, comment: *"418/429 rate-limit bans must not exit the loop."* The reconciler simply never mirrored the pattern.

## Fix

`pkg/execution/binance_live.go` (commit `5854501`, branch `fix/reconciler-rate-limit-backoff`):

- `isRateLimitErr(err) bool` — classifies `positionRisk 418/429` (6-case unit test).
- `PositionReconciler.RateLimitBackoff` (default `120s`, **must exceed** PollInterval) — on a rate-limit response the `Run` loop stops polling for this cooldown via `sleepBackoff` (ctx-aware), long enough for the ban to expire instead of being re-extended.
- Applied at both reconcile sites in `Run` (initial + ticker).

TDD: 2 tests RED→GREEN (`TestIsRateLimitErr_Classifies418And429`, `TestPositionReconciler_Run_BacksOffOnRateLimit`). `go test ./pkg/execution/` green; `go build ./...` + `go vet` clean.

120s vs the aggTrade poller's 60s: reconciler calls are rarer and a missed reconcile cycle costs only staleness-alert latency (not data loss), so a longer cooldown that comfortably outlasts a short ban is the safer trade.
