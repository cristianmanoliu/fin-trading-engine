## Incident: ENS 07-07 04:00 UTC Layer 3 order rejected with -1109 "Invalid account"

The first cap-fitting KAVA/ENS live signal after the `d08ee30` quantization
fix (2026-07-04) fired on ENS 07-07 04:00 UTC. The Layer 3 shadow executor
built the order (quantization now correct — 0.98 units at $4.187 fits the
0.001 step and is inside `[minQty, maxQty]`), signed the request, and got
back:

```
4xx 400: {"code":-1109,"msg":"Invalid account."}
```

not a -2014/-2015 auth rejection and not a -1111/-1013 filter rejection.
That distinction is diagnostic.

### Direct account inspection (from VPS, using the loaded testnet creds)

Signed calls succeed on read endpoints but the account state is empty:

- `GET /fapi/v2/balance` → `[]` (empty asset list)
- `GET /fapi/v2/positionRisk?symbol=ENSUSDT` → `[]` (well-formed empty)
- `GET /fapi/v2/account` →
  ```
  {"feeTier":0,"canTrade":false,"canDeposit":false,"canWithdraw":false,
   "updateTime":0,"totalWalletBalance":"","availableBalance":"",
   "assets":[],"positions":[]}
  ```
- `POST /fapi/v1/order/test` (dry-run) → empty-shell success response.
- Real `POST /fapi/v1/order` → -1109.

Interpretation:

- **Credentials are valid** — signatures verify, read endpoints return
  well-formed responses, dry-run POSTs succeed.
- **The account is dormant** — `canTrade:false`, `updateTime:0`,
  `assets:[]`, `positions:[]`. Binance testnet accounts periodically get
  wiped or auto-expire; the account still exists at the auth layer but has
  no wallet/margin state, so any real (non-`/order/test`) order at any
  size returns -1109.
- **This is NOT a repeat of the June -1111 quantization bug.** The order
  passed our qty guard cleanly. The failure is exchange-side account
  state, not order shape.
