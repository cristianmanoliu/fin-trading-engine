# 2026-06-09 — The Bollinger phantom-fill bug: non-EMA modes ignored `--side-filter`

## TL;DR

`--side-filter short` was enforced in **only 2 of 10** entry modes
(`checkEMACrossover`, `checkFundingCross`). The other 8 — including **Bollinger
(bb20, a deployed shadow)**, RSI, MACD, Momentum, VWAP, PDH/PDL, Absorption,
Breakout — silently emitted **LONG** signals when their pattern said "long," even
under `--side-filter short`. A long target sits ABOVE entry, so when price rose, the
trade hit that above-entry target and was booked as a **TARGET "win"** — a short
position recording profit while price moved against it. **Phantom profit.**

**Impact (bb20, 57-symbol, 2020-2021 bull):**
- Reported: **+$559,132**
- Phantom (TARGET wins with exit ≥ entry): **+$2,249,659** across **427 trades**
- **Corrected: ≈ −$1,690,527.** bb20 doesn't win the bull — it loses ~$1.7M.

The live deployed config (EMA 9/21) is **CLEAN** — `checkEMACrossover` had the inline
filter (0 phantom trades, verified). No real-money exposure. But every non-EMA
backtest number in the repo's history is contaminated, and bb20 is a live shadow.

## How it was found

The per-year backtest (regime-switch continuous baselines) showed bb20 as the ONLY
config without back-to-back red years AND the highest total (+$1.81M) — uniquely
escaping the bull-year bleed that kills every EMA config. That uniqueness was the
tell: bb20 is a downside-breakdown short (`close < lower band`), which should bleed
in a bull like every other short. Dissecting BTC bb20 2020-2021 trades:

```
TARGET wins: 24; of those with exit >= entry: 15   ← impossible for a real short win
  entry=7757 exit=9151 target=9151 outcome=TARGET pnl=+$5,769   (price ROSE, "won")
  entry=24605 exit=30718 target=30718 outcome=TARGET pnl=+$5,754
  ... 15 total, all with target ABOVE entry
```

`target` ABOVE `entry` is the signature of a **LONG** signal. These were bullish
breakouts (`close > upper band`) that should have been dropped by `--side-filter
short` but weren't.

## Root cause

`pkg/strategy/entry.go`. The `Evaluate` dispatcher routed to a per-mode
`check*` method. Only two of those methods contained the
`if cfg.SideFilter != Neutral && side != cfg.SideFilter { drop }` guard:

| method | SideFilter applied? |
|--------|---------------------|
| checkEMACrossover (live config) | ✅ line 909 |
| checkFundingCross | ✅ line 699 |
| checkBollingerBreakdown (bb20) | ❌ |
| checkRSIBreakdown | ❌ |
| checkMACDCross | ❌ |
| checkMomentum | ❌ |
| checkVWAPDeviation | ❌ |
| checkPDHPDLBreakFixedRR | ❌ |
| checkAbsorption | ❌ |
| checkBreakout | ❌ |

The per-mode signal-generation math is correct (a long signal correctly has
target = close + risk×rr, above entry). The bug is purely that the **side-filter
drop was missing** for 8 modes, so long signals survived a short-only run.

## The fix

Enforce `SideFilter` **centrally** at the dispatch seam, for ALL modes:

```go
func (e *EntryDetector) Evaluate(levels []float64, vwap float64, bias *BiasTracker) *models.Signal {
    return e.applySideFilter(e.evaluateRaw(levels, vwap, bias))
}

func (e *EntryDetector) applySideFilter(sig *models.Signal) *models.Signal {
    if sig == nil { return nil }
    if e.cfg.SideFilter != models.Neutral && sig.Side != e.cfg.SideFilter {
        return nil
    }
    return sig
}
```

`evaluateRaw` is the old dispatch body, unchanged. The two inline per-method
filters (EMA, funding) are left in place — now redundant (double-filtered, same
result) and harmless; they keep their existing tests green. **Do not re-add
per-method SideFilter checks — the chokepoint is `applySideFilter`.**

### Verification

- bb20 BTC 2020-2021 after fix: **LONG trades 0** (was 58), **phantom 0** (was 15),
  pnl **−$61** (was +$24,921). The phantom longs were the entire "profit."
- `go test ./...` — all 14 packages green (the double-filtered EMA path is byte-
  identical).
- New regression tests (`pkg/strategy/entry_test.go`):
  - `TestBollingerSideFilter_BlocksLongBreakout` — bullish breakout under
    SideFilter=Short emits no signal.
  - `TestBollingerSideFilter_AllowsShortBreakdown` — bearish breakdown still emits
    a valid Short, and asserts `TakeProfit < EntryPrice` (directly guards the
    phantom-win mechanism).

## Blast radius — what this invalidates

**The user's instinct was right: this is a class bug, and likely every "profitable"
non-EMA backtest is affected.** Any historical finding produced with `--side-filter`
on a non-EMA mode is contaminated by phantom longs:

- **bb20 (deployed shadow) — BACKTEST profitability is the artifact.** In the bull
  backtest (2020-2021), corrected bb20 is the WORST config (−$1.7M), not the best.
- **bb20 LIVE shadow journal — AUDITED 2026-06-09 (opposite sign, reassuring):** the
  bug DID fire live — **29 of 62 closes were illegitimate LONG trades** (should be 0
  in short-only). But unlike the bull backtest, the live window (May-June 2026) is
  crypto FALLING, so the bug's longs got STOPPED OUT: 29 longs, 7% WR, **−$16,822**.
  Decomposition of the +$39,383 reported realized:
  - **legit shorts: 33 trades, 42% WR, +$56,205**
  - **illegit longs: 29 trades, 7% WR, −$16,822**
  So live bb20 is **understated, not inflated** — clean (shorts-only) it'd be +$56,205;
  the bug COST it $16,822 by forcing losing counter-trend longs. Same bug as the
  backtest, opposite sign, because the regime flipped (bull→bear). Current open book
  (24 positions) is all-short, clean. **No real money at risk (shadow, promotion-
  LOCKED), no correction needed — but the VPS binary should be redeployed so bb20
  stops trading phantom longs going forward.** This does NOT rescue bb20: clean live
  +$56k is the same non-promotable shadow-vs-live distortion (frequency/censoring/
  selection) as the other shadows, and the bull-backtest −$1.7M truth stands.
- Any past RSI / MACD / Momentum / VWAP / PDH-PDL / absorption / breakout sweep run
  short-only — re-verify before trusting.
- **The live deployed EMA 9/21 config is unaffected** (clean inline filter, verified
  0 phantom). The forward-paper live numbers stand.

## Strategy implication

bb20 was the one config that appeared to escape the operator's back-to-back-red-year
intolerance. That escape was the bug. **Corrected, ALL 9 cohorts have the
consecutive-red bull problem** — the bull-year bleed (2020-2021 red) is universal and
structural to always-short trend/breakdown strategies. There is no config in the
tested set that avoids it. This removes the last "maybe bb20" thread from the
strategy-class decision.
