### Track 10: Telegram message size truncation (commit `214f724`)

The Telegram API enforces a 4096-char hard limit on the `text` parameter
(https://core.telegram.org/bots/api#sendmessage). Neither
`scripts/lib/notify.sh` nor `pkg/notify/telegram.go` truncated outbound
message bodies before POST.

**Real fail-open shape**: oversized message → HTTP 400 from Telegram →
curl/Go HTTP non-zero → retry loop hits the same too-long body → all
retries fail → **alert silently drops**. Same silent-on-corrupt-input
pattern (locked across 6 paired implementations as of this morning)
applied to OUTBOUND API contracts: malformed-by-size payload maps
silently to no-op.

Most existing callers use `tail -3` / `tail -1` to bound subprocess
output included in bodies, so the failure mode is rare today. But:
1. Future callers might forget the tail-bound
2. `tail -3` of a script with absurdly long lines still exceeds 4096
3. Go cmd/engine error-paths can embed long stack traces

Truncating at the notify helper boundary locks the contract so EVERY
invocation is safe by construction.

**Bash side**: `_notify_truncate_text` factored as a sourceable helper.
`notify_telegram` calls it on the joined `prefix+subject+body` BEFORE
curl. Marker `…[truncated]` appended.

**Go side**: `truncateTelegramText` rune-based truncation (slightly
conservative for UTF-16 emoji surrogate pairs — under-fill is safer
than over-size rejection). `sendStructuredAt` calls it after composing
msg + optional aggregation footer, before `sendWithRetry`.

**Pattern extension** (genuinely new for this lens): silent-on-corrupt-input
now extends to OUTBOUND API contracts. Previously locked only at
INBOUND boundaries (journal parsing, ssh-fetch, etc.). Today's lens
applied symmetrically to the side of the code that talks TO external
services. This is a meaningful extension of the pattern's reach.

5000 / 4097 truncation + prefix preservation.
