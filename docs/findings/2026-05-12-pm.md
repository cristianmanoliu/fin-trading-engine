## Post-smoke probe: testnet vs demo-fapi endpoint duality

Sequel investigation after the smoke PASS. User had shared:
- Spot Demo docs: `developers.binance.com/docs/binance-spot-api-docs/demo-mode/general-info`
- Futures Demo API: `demo-fapi.binance.com`
- Futures docs index: `developers.binance.com/docs/derivatives/`

Question: is `testnet.binancefuture.com` being deprecated in favor of
the newer Demo Mode at `demo-fapi.binance.com`?

**Evidence gathered:**

1. **Binance docs explicitly state Demo Mode is parallel, not replacement.**
   Direct quote from Spot Demo docs: "SPOT Testnet is useful to integrate
   with upcoming features not yet available on the live exchange. Demo
   Mode is useful to test against realistic market data."

2. **No deprecation notice for testnet.binancefuture.com** in the 2024–2025
   Binance Derivatives changelog. The 2024-01-24 entry updated its
   WebSocket URL (to `wss://fstream.binancefuture.com`), confirming
   continued maintenance.

3. **Demo Mode Spot endpoints are `demo-api.binance.com` (REST) +
   `demo-ws-api.binance.com` (WS).** The Futures Demo URL the user
   shared (`demo-fapi.binance.com`) is NOT documented in the Spot Demo
   page — but it resolves and responds.

4. **Empirical probe (this session): same backend.** Signed
   `GET /fapi/v2/account` call with the user's testnet credentials against
   BOTH endpoints returned IDENTICAL responses (wallet balance 5000 USDT,
   all flags equal, same updateTime). Conclusive: `demo-fapi.binance.com`
   is an alias/mirror for `testnet.binancefuture.com`, not a parallel
   service with separate credentials.

**Conclusion: NO code change needed today.** The existing
`pkg/execution/binance_live.go:111` constant
`TestnetAPIBaseURL = "https://testnet.binancefuture.com"` is correct
and supported. The `demo-fapi.binance.com` URL is an equivalent
alternative the operator could use today without code change (env
override path: `kill_switch` already supports `BINANCE_API_BASE`;
`cmd/engine` does not — that's an inconsistency, not a defect).

**Watch-for trigger**: if Binance announces deprecation of either URL,
or if their behavior diverges (different serverTime, different
exchangeInfo cache), add `BINANCE_TESTNET_BASE_URL` env override to
`cmd/engine` for symmetry with `cmd/kill_switch`. Until then, the
single const is honest about the production endpoint it points at.

## Latent bugs surfaced by first real run

### L2-6 — `--symbol` flag bug (HIGH)

Harness invocation since original commit `3199be8` (2026-05-10):
```
$ENGINE_BIN --config configs/default.yaml --symbol $SYMBOL --executor binance_live_testnet
```
But `cmd/engine` has NO `--symbol` flag — symbol is sourced from
`cfg.Symbol` via the YAML's `symbol:` key. Engine exited rc=2
("flag provided but not defined") within 100ms.

Phase 4 then misclassified the early exit as `engine-crashed-early` /
`SMOKE_FAIL_OTHER` (exit 6, CRITICAL Telegram tier) — the wrong
diagnostic, wrong tier. Operator following the dashboard literally
would have investigated "engine crash" when the root cause was harness
mis-invocation.

**Latency**: the bug had been present and untested for 2 days
(`3199be8` 2026-05-10 → first real run 2026-05-12 PM). DRY_RUN PASSED
throughout because DRY_RUN skips the actual `timeout cmd/engine`
invocation and writes a synthetic clean log.

**Fix**: introduced `SYMBOL → configs/<lowercased>.yaml` resolution
(portable `tr` for macOS bash 3.2), existence-check before phase 2
that dies as `SMOKE_FAIL_ENV` (operator misconfig — correct tier, not
CRITICAL), update both DRY_RUN echo + real invocation to reference
the resolved config. New test class `SymbolConfigResolutionTest`
covers both happy path (BTCUSDT → resolves cleanly) and
unknown-symbol-yaml diagnostic.

### L2-7 — backfill-grep msg-text drift (HIGH)

After L2-6 fix, the engine ran the full 5-min smoke window cleanly.
But the harness reported `backfill-incomplete` (exit 6) — false
negative. Inspecting the log:

- Engine emits at `pkg/marketdata/binance.go:220`:
  `slog.Info("kline backfill complete", ...)` → JSON
  `"msg":"kline backfill complete"`.
- Harness grepped at line 308 (pre-fix):
  `grep -cE '"msg":"backfill complete' "$LOG_FILE"` — requires
  "backfill" IMMEDIATELY after `"msg":"`. The literal "kline " sits
  between, so the regex never matches.

The DRY_RUN synthetic log (line 242 pre-fix) wrote:
  `{"level":"INFO","msg":"backfill complete","symbol":"$SYMBOL"}`
— matching the WRONG-but-consistent pattern. Both sides of the
DRY_RUN test path agreed with each other but disagreed with reality.
**DRY_RUN PASSED while real smoke FAILED** even when the engine had
completed backfill cleanly in 1.1s (5,760 klines, 4 pages, 23,040 ticks).

**Pattern**: writer-equals-fixture drift, adjacent to writer-equals-model
(`docs/AUDIT_LENS.md` adjacent-pattern 2026-05-10-pm). The fixture
and the regex moved in lockstep with each other but neither was
pinned against the live writer.

**Fix**: update HAS_BACKFILL regex + DRY_RUN heredoc msg string in
lockstep + new test class `FixtureMsgVsEngineEmitTest` that parses
the harness fixture + grep regex and asserts each appears as a
substring in the live engine Go source (`pkg/marketdata/binance.go`,
`pkg/marketdata/heartbeat.go`, `cmd/engine/main.go`). 3 assertions:
"kline backfill complete", "heartbeat" (canonical return string),
and the TESTNET-EXECUTOR-ACTIVE marker. Future engine refactor that
renames any of these emit-points fails CI before reaching production.

## Pattern observations

### DRY_RUN coverage has a structural blind spot

The harness was DESIGNED with DRY_RUN as the test-only path
(env-vars, network, build, log-analysis). The engine invocation was
deliberately excluded from the test surface for cost/isolation reasons.
But the test surface DOES include the DRY_RUN synthetic log generator
+ the analysis-phase grep regexes. **Those two co-evolved with each
other instead of evolving against the live engine emit-points.** Result:
12 tests PASSED that didn't validate the contract they were nominally
testing.

The new `FixtureMsgVsEngineEmitTest` closes this — it pins the fixture
AND the regex against the live Go source. It's a meta-test, in the
spirit of `scripts/test_criterion_coverage.py` (T15 2026-05-11) but
for log-line text contracts instead of locked numeric constants.

### Spec-impl-drift now extends to log-line-text-drift

Earlier today's 4 flavors of spec-impl drift (value / label / staleness
/ latent) gain a fifth: **emit-string drift** — when two parties (writer
+ consumer of slog output) hold independent literal-string assumptions
that diverge. Same family as the locked enforcement-pattern; the new
test pin handles this class symmetrically to how `test_criterion_coverage`
handles numeric constants.
